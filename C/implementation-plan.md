# PDF Viewer SDK MVP — Implementation Plan

## Goal

Deliver a reviewer-runnable React/TypeScript PDF viewer SDK and demo client in a GitHub repository. The SDK must expose viewer and editor capabilities as a reusable component/API, while the demo proves how a client application integrates it. The project must run with `npm install && npm run dev`.

## Scope and acceptance decisions

| Requirement | MVP implementation decision | Evidence of completion |
| --- | --- | --- |
| Browser PDF fidelity | PDF.js canvas/text-layer rendering; use its Web Worker | Selectable text and crisp high-DPI pages in the demo |
| Large-file fast display | PDF.js HTTP range requests; demonstrate through the networked sample/document loader | `disableRange: false`, `disableStream: false`; documentation explains a server must support byte ranges and linearized PDFs benefit most |
| Zoom/navigation/modes | Zoom in/out, percentage, fit width, fit page, continuous/single-page, thumbnail and page-number navigation | Automated state tests + manual checklist |
| Rotate/reorder/import/extract | In-memory edit transaction using `pdf-lib`; render from generated bytes after commit | Fixture tests inspect page count/order/rotation |
| Export/local save | Download the current document or a selected page range | Download smoke test/manual evidence |
| Print | Isolated print document/window with rendered page images, then browser print | Manual checklist |
| Bonus WASM features | Optional MuPDF WebAssembly worker adapter. Implement only APIs that can be verified in browser. Do not claim unavailable signature creation as complete. | Capability table and tests/manual proof |

## Technical approach

### Stack

- React + TypeScript + Vite
- PDF.js (`pdfjs-dist`) for progressive browser viewing, text selection, thumbnails, and rendering
- `pdf-lib` for reliable client-side page mutation and serialization
- Optional MuPDF.js WebAssembly worker for native annotation/redaction/bookmark capabilities where the installed browser API supports them
- Vitest + React Testing Library for unit/component tests; Playwright for end-to-end smoke paths

## Delivery sequence

### 1. Plan and project foundation (15 minutes)

1. Create the repository and the required `A`, `B`, and `C` directories.
2. Place this finalized plan at `C/01-implementation-plan.md` before implementation begins.
3. Scaffold a TypeScript/Vite React app in `A` and verify a clean `npm install && npm run dev`.
4. Add a small, redistributable PDF fixture and a second fixture for merge/reorder tests. Do not commit confidential PDFs.
5. Write the public SDK types first, so the demo consumes the same contract a real client would.

### 2. Viewer foundation (30 minutes)

1. Configure the PDF.js worker through Vite asset URLs.
2. Implement `loadDocument(source)` for `File`, `ArrayBuffer`, and URL sources.
3. Render pages at device-pixel-ratio scale with an aligned text layer for selection/accessibility.
4. Add page status, previous/next controls, direct page input, and thumbnail navigation.
5. Add zoom in/out with bounded scale plus explicit fit-width and fit-viewport calculations based on the viewer container.
6. Add continuous and single-page modes. In single-page mode, preserve the active page and rerender only that page.
7. Enable PDF.js range/stream options and document the server prerequisites for progressive/linearized delivery.

### 3. Editing workflow (40 minutes)

1. Model changes as an edit transaction: `originalBytes` remain immutable; `workingBytes` update only after a successful operation; `isDirty` drives the UI.
2. Use `pdf-lib` to rotate selected pages, move/reorder pages, merge an imported PDF, extract selected pages, and serialize/download results.
3. Provide an editor toolbar and a reorder panel with accessible move-up/move-down controls. Drag-and-drop may be added only after keyboard controls work.
4. On each committed operation, reload the generated bytes into PDF.js, retain the active page when valid, and record an undo snapshot.
5. Add undo/redo for the transaction history, capped to a modest number of snapshots to control memory.
6. Warn before discarding unsaved edits when loading another document.

### 4. Printing, export, and local save (15 minutes)

1. Implement whole-document or selected-range export through `pdf-lib` page copying.
2. Create object-URL downloads with a named PDF file and revoke URLs after use.
3. Implement print by opening a print-focused document containing rendered page images at print scale, waiting for images to load, then calling `print()`.
4. Mark browser print behavior as browser-dependent, but make the action usable without a backend.

### 5. WebAssembly bonus pass (20–30 minutes, strictly time-boxed)

1. Place MuPDF initialization and all mutations in a dedicated worker boundary so WASM never blocks React rendering.
2. Feature-detect the exact installed MuPDF.js API; create a capability object surfaced in the UI and documentation.
3. Implement verified features in this order: rectangle redaction preview/apply, text highlight/note annotation, bookmark read/write, existing widget inspection.
4. Signature-widget creation is out of scope unless the actual browser MuPDF.js API exposes an equivalent tested creation API. State the limitation honestly.
5. Preserve a functional core if the WASM bundle/API is unavailable.

### 6. Quality, docs, and submission evidence (30 minutes)

1. Write Vitest coverage for page operations, zoom/fit calculations, export page selection, dirty state, and worker capability fallback.
2. Add Playwright tests for loading, navigation, zoom, continuous/single mode, rotation, reorder, merge, extract/export, and print-action availability.
3. Run lint, type-check, unit tests, end-to-end tests, and a production build.
4. Manually verify the browser flow using both fixtures, keyboard-only navigation, and a narrow viewport.
5. Capture the exact commands/results in `C/04-validation.md`.
6. Complete `B/architecture-and-design.md` and the root README with setup, sample integration, supported browsers, limitations, and feature/capability table.
7. Save the authorized Codex AI usage transcript/log as `C/02-ai-usage-transcript.md`. Its heading must plainly state that Codex was the approved substitute for Cursor; do not fabricate a Cursor export. Write the human review explanation in `C/03-ai-output-changes.md`.

## Requirements inferred from the client-integration video

The video is incomplete, so the implementation will make these explicit, practical SDK requirements rather than assuming an internal application owns them:

1. **Embeddable API:** Client passes a URL, uploaded file, or byte buffer; no server dependency is required for local files.
2. **Lifecycle callbacks:** Client receives document-load, page-change, edit/dirty-state, exported-file, and error events.
3. **Controlled integration points:** Consumer can set initial page/view mode and can hide editing/printing/export controls via a feature configuration object.
4. **Reliable edit semantics:** Operations are local, explicit, reversible before export, and never overwrite the input file.
5. **Operational feedback:** Loading/progress, page count, active page, current zoom, errors, unsaved state, and disabled actions are visible to the user.
6. **Accessibility:** Semantic buttons with labels, keyboard-safe page control/reordering, focus handling after document reload, and text-layer selection.
7. **Security/privacy:** Files remain in the browser for this MVP. Remote URLs require normal browser CORS access; range loading requires `Accept-Ranges: bytes` from the host.

## Definition of done

The MVP is ready to submit only when all items below are true:

- `npm install && npm run dev` works from the documented directory.
- A reviewer can load a local PDF and a URL-based PDF.
- View, navigation, zoom/fit, continuous/single-page mode, edit operations, export/local save, and Print are demonstrable.
- The feature table distinguishes core, verified bonus, and unsupported APIs without exaggeration.
- `A`, `B`, and `C` folders are committed, including plan, architecture, AI evidence, explanations, and validation record.
- README tells the reviewer how to run, test, and exercise the demo in under five minutes.
- Git history has small, legible commits: scaffold/viewer, editor/export, tests/docs/submission artifacts.

## Risks and controls

| Risk | Control |
| --- | --- |
| MuPDF browser package/API differs from examples | Keep it as an isolated optional adapter; protect the required core with PDF.js + pdf-lib |
| Linearization cannot be guaranteed from a client | State the dependency accurately: linearized input plus a range-enabled HTTP server; validate range behavior in DevTools |
| `pdf-lib` can alter advanced PDF features on save | Preserve source bytes until an edit/export; document that edits create a fresh output file |
| Print layout varies by browser | Render deterministic images into a print window and test Chrome; label browser print as browser-dependent |
| Interview timebox pressure | Finish the core path and evidence first. Bonus work is a fixed final timebox, not a blocker |
